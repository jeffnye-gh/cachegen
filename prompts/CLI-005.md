## Results Assessment

Field consumption

The tool now reports which configuration fields no stage reads. For pacino it found 74 unconsumed leaves out of 287. The CLI-005 hypothesis, written from CLI-004's observations, named seven. The estimate was off by an order of magnitude because it was made from memory rather than measurement, which is the same failure as CLI-003, where two uncovered diagnostic codes were reported and the mechanism found 21.

Two implementation choices determine whether that number means anything.

The first is that a field being checked for presence does not count as being read. The T-6 group completeness check asks whether a field exists and never looks at its value. If presence counted as a read, the entire maintenance group and most of miss_handling would be reported as consumed.

The second is that the record is made in the accessor rather than where the value is extracted. NodeCtx::build() extracts inclusion into a member, and no caller ever invokes NodeCtx::inclusion(). Marking at extraction would report the field as consumed. Four of NodeCtx's fifteen accessors have no callers.

Either choice made the other way produces a report that appears to work and measures nothing. Both belong in the decision record, because anyone adding a stage needs to know which convention applies.

Logs.EditingAnUnconsumedFieldChangesNothingEmitted converts the report into a test: it selects a field from the report at run time, edits it, re-emits, and diffs the two trees. That is a stronger assertion than the report itself.

The feature table's three categories

The table reports 216 features, 35 covered and 181 not. The 181 divides into 74 that no stage reads and 107 that are consumed but not observable from a port.

Those 107 are not all the same. The 44 link fields shape the port list, and a wrong value fails to compile rather than failing a test. The IA says so directly, and compilation is a stronger check than a testbench assertion. Grouping them with genuinely untested features understates what is verified.

A third category value would fix this: build for features verified by the design compiling, alongside test and inert. The current table invites a reader to conclude that 35 of 216 features are verified, when the accurate statement is that 35 are verified behaviorally, roughly 60 are verified structurally by the build, and 74 are not verified because nothing reads them.

read_latency_cycles

read_latency_cycles is honored by the memory model and by none of the three caches. The emitted cache has whatever latency the pipeline happens to produce, and no emitted file states that the configured value was ignored.

This is more serious than the other inert fields. inclusion being inert is discoverable, because the design has no probe path and a reader who investigates finds that out. A latency number is a value an architect would use directly, and it is among the most likely fields to be edited during exploration, which is the tool's purpose.

The immediate fix is one line in the emitted control's header stating that the declared latency is not honored, matching what is already done for mshrs. The actual fix requires a configurable read pipeline depth with tag_compare_stage selecting where the tag compare lands.

There is a secondary issue. This field is consumed on mem and inert on the three caches. The report is per leaf, so it can say /caches/l2/timing/read_latency_cycles is unconsumed, but it has no way to express that one field name has different consumption depending on node type. That will matter as more fields become partially consumed.

The bank field ruling

The ruling is applied and l2's bank select moved from bit 15 to bit 6. The IA states that no functional test can distinguish the two placements, and that is correct: two addresses differing in bit 6 are in different banks under the new ruling and in different sets under the old one, and a correct cache serves both.

It also states that the CLI-004 corroboration never separated them either. Taking N bits from either end of the index leaves N bits, so the check that the set index width agrees with sets-per-bank passes under both readings. That check validates the arithmetic, not the position. Saying this rather than letting the check stand as evidence is the right handling.

Bank.L2DecomposesAsTheRulingSays asserts the derivation matches the ruling, which catches drift but is not independent evidence that the ruling is correct.

The consequence is that a misplaced bank select is a performance defect, and nothing in the tree measures cycles. The functional model in CLI-006 will not detect it either. This is the second finding in this task that points at the absence of performance measurement, the first being read_latency_cycles.

The deletion itself is well justified on D-37 grounds: position is derivable from granularity, so bank_select_position was a derived value in the input, which D-37 forbids. That reasoning generalizes and should be recorded as a rule rather than as a one-time decision.

## Background

The build must never resolve a tool from PATH. A generated
Makefile that says `verilator` runs whatever the user happens to
have, and the version that ran produced ten warnings under -Wall
with warnings as errors. Whether Verilator 5.048 produces the same
ten is not known and R-5 does not depend on the answer.

The nine increment defects are one shape:

```
  abeat <= L2BeatIdxBits'(abeat + 1);
```

The literal 1 is a 32 bit int, so the addition happens at 32 bits
with the narrow operand expanded, and the cast truncates the
result afterward. The cast cannot undo an expansion that already
occurred. See R-5.

Seven fields are carried and unread: arbitration on all eleven
interfaces, mshrs, mshr_targets, victim_buffer_entries,
fill_buffer_entries, inclusion, write_throughput_cycles, and
way_access carried since CLI-002. A user can edit any of them,
re-emit, and get byte identical output with nothing said. That is
the CLI-003 defect one level up: a field that does nothing and a
field that works are indistinguishable from outside.

### R-7, the bank field, ruled

`bank_select_position` is DELETED from
`planning/schema/caches.schema.json`, both the property and the
`then.required` entry of the `banks >= 2` conditional, and from
both sites in `testcases/pacino/pacino_caches.json`. Those are the
only two files this requirement touched.

**The derivation.** line granularity means consecutive lines
alternate banks. That is the definition, and it puts the select at
the bits IMMEDIATELY ABOVE THE OFFSET, which is the bottom
bank_bits of the index. The set index is what is left, above it.

**l2's decomposition, before and after.**

```
  l2, 512 KB, 8 ways, 64 B lines, 2 banks, line, pa_bits 32

                       CLI-004                 CLI-005
  offset               [5:0]     6 bits        [5:0]     6 bits
  index                [15:6]   10 bits        [15:6]   10 bits
  tag                  [31:16]  16 bits        [31:16]  16 bits

  bank                 [15:15]   1 bit         [6:6]     1 bit
  set index            [14:6]    9 bits        [15:7]    9 bits
```

The three fields are unchanged. What moved is where inside the
index the select is taken from: the TOP bit under above_index, the
BOTTOM bit under the granularity rule.

And mem, which declares 8 banks and the same granularity:

```
  mem, 1 GB, 1 way, 64 B lines, 8 banks, line

                       CLI-004                 CLI-005
  bank                 [29:27]   3 bits        [8:6]     3 bits
  set index            [26:6]   21 bits        [29:9]   21 bits
```

**Why the field had to be deleted rather than chosen between.**
pacino declared `line` and `above_index` together and the two
readings of that pair disagree: line interleaving IS the bits above
the offset, and above_index is the other end of the index. One
field cannot disagree with itself. The corroboration was never
going to separate them either, which is the next point.

**The independent check CLI-004 built stays, and it is honest
about what it can and cannot do.** geometry.cpp still requires that
the set index the field arithmetic leaves and the sets-per-bank the
division gives are the same number, and still refuses to resolve
the field if they disagree:

```
  l2    field arithmetic leaves 9 bits    2**9  = 512
        sets_per_bank = 1024 / 2         = 512     agree
  mem   field arithmetic leaves 21 bits   2**21 = 2097152
        sets_per_bank = 16777216 / 8     = 2097152 agree
```

It passes under BOTH readings, because taking N bits from either
end of the index leaves the same number of bits. It is a check on
the arithmetic, not on the position, and it was never the thing
that made above_index look right. Stating that is part of R-7's
answer: the check is kept because it catches a real class of error,
and it is not evidence for either ruling.

**word granularity remains unresolved and reports why**, exactly as
CLI-004 left it. `Bank.WordGranularityIsUnresolvedAndSaysWhy`
reaches the live path by editing a copy of pacino, so the note is
exercised rather than taken on trust. The note:

```
  bank_interleave_granularity is word, which puts the select
  inside the line offset rather than in the index, and leaves
  sets_per_bank derived as sets / banks disagreeing with every
  bank holding every set
```

### R-9, the memory images

**The format, in full.** Plain text. A header of `key value` lines,
then `entries` lines of one location each. Chosen for a C++ reader
as much as for a diff: every field is fixed width hex, the order is
ascending address, and NOTHING VARIES between two runs of one test.
No timestamp, no cycle count, no path, no host.

```
  cgen-memimage <version>
  system     <system name>
  node       <node name>
  point      <the name the test gave this image>
  addr_bits  <address width in bits>
  data_bits  <width of one location in bits>
  beat_bytes <bytes per location>
  line_bytes <the node's line size, for a reader grouping lines>
  entries    <how many lines follow>
  <addr> <data>
  ...
```

```
  addr   addr_bits/4 lower case hex digits, zero padded, the BYTE
         address of the location
  data   data_bits/4 lower case hex digits, zero padded, most
         significant nibble first
  order  strictly ascending by addr, and every address is a
         multiple of beat_bytes
```

A location is one BEAT, which is the granularity the memory model's
store keys on. The header says the beat width so a reader never has
to assume it. Only locations a test actually touched appear:
the store is sparse because the node is 1 GB.

**A worked example.** `output/pacino/images/pacino_after_evict.mem`,
the image taken immediately after the eviction test. The complete
head and the first three entries:

```
  cgen-memimage 1
  system pacino
  node mem
  point after_evict
  addr_bits 32
  data_bits 256
  beat_bytes 32
  line_bytes 64
  entries 10
  00450000 000000000000000000000000000000000000000000000000000000
           00c0de0001
  00450020 000000000000000000000000000000000000000000000000000000
           00c0de0002
  00460000 000000000000000000000000000000000000000000000000000000
           00beef0000
```

The data lines are shown wrapped here to fit 80 columns; in the
file each is one line of 8 + 1 + 64 characters. Reading it: the
line at byte 0x450000 was evicted and it carries 0xc0de0001 in its
first word, which is the value the test wrote at that address, and
0xc0de0002 in the second beat at 0x450020, which is the value the
beat-structure test wrote 32 bytes higher. That is the write_back
check, in a file, for the functional model to compare against.

The empty case, `pacino_after_write.mem`, is the whole file:

```
  cgen-memimage 1
  system pacino
  node mem
  point after_write
  addr_bits 32
  data_bits 256
  beat_bytes 32
  line_bytes 64
  entries 0
```

`entries 0` and no lines. That is the assertion "the written line
has not reached memory", recorded rather than only checked.

**Which tests emit an image, at what points, and where.**

The top level testbench, `output/pacino/tb/pacino_tests.svh`, at

| Point | When | What it records |

**Where the code lives.** `cg_dump_image` is a task in the memory

That is what MKDIR is on the tool list for.

## Deferred Work

### 1. read_latency_cycles is honoured by the memory and by NO CACHE.

The unconsumed report says so for l1i, l1d and l2, and nothing else
in the tree does. A configuration that asks for a 12 cycle L2 gets
an L2 whose read latency is whatever the emitted pipeline happens
to be, and the emitted file does not say so.

This is worse than the inert fields around it, because
read_latency_cycles is a number a user would reasonably believe.
`tag_compare_stage` is in the same position and is the field that
would decide part of it.

The fix is a task, not a note: the cache control needs a
configurable read pipeline depth, and `tag_compare_stage` needs to
select where the compare lands in it. Until then the emitted
control's header should say the declared latency is not honoured,
the way it already says mshrs sizes nothing.

### 2. The three top level tests that could not be written.

R-8 asks for a test for every feature or a statement of why not,
and the 181 uncovered features are stated above. Three of them are
worth separating out, because they are not inert and not
unobservable, they are simply not reachable through the ports this
design has:

```
  a) TL-C's B, C and E channels on the l1d to l2 link. The
     conformance level is consumed, the signalling is emitted, and
     it is tied off, so a test can only show that tying it off did
     not break A and D. That is what "the word in the second beat
     reads back" does and it is not a test of TL-C.

  b) source_bits, on every TileLink link. The width is consumed and
     shapes the port. Exercising it means several requests in
     flight with distinct ids, and the cache is blocking, so there
     is never more than one.

  c) maintenance. Four fields on three nodes, twelve leaves, and no
     maintenance port is emitted at all. It is not that the test
     is hard, it is that there is nothing to drive.
```

All three become testable in the same task: a non blocking cache
with a probe path. That task also makes mshrs, mshr_targets,
