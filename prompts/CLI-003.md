# Task Overview

Two guard tests and the fixtures one of them requires.

The first asserts that every schema file declares the JSON Schema
draft the tool's validator actually implements. The second asserts
that every diagnostic code the tool can emit has a negative fixture
that produces it.

The second test is the point of the task. T-3 was silently dead
through the whole of CLI-001 and was found by accident during
CLI-002. A check that fires on nothing and a check that passes are
indistinguishable in the current output. This test makes them
distinguishable.

Part of this work may already be present in the tree. Read before
writing. See R-1.

## Results Assessment

21 of 37 codes had no fixture. CLI-002 reported two. The suite was 31 of 31 green with more than half the tool's diagnostics never having fired in the life of the project.

That settles the hypothesis in the strongest possible way, and it retroactively tells you what the CLI-001 and CLI-002 green suites were worth. T-3 was not an unlucky one-off. It was the one instance that happened to be found.

The test itself looks sound. Deriving the expected set from the list at run time, enumerating the fixture directory rather than listing it, and asserting the Guard direction as well as the Fixture direction are all the right calls. The three deliberate breakages, each run and observed to fail with the right message, are the part that makes the test credible rather than merely present.

One boundary worth being clear on: this proves a code can fire, not that it fires on the right condition. Since each new fixture asserts exactly one diagnostic, the coverage is reasonable, but a check with an inverted or misfielded condition that still fires somewhere would pass. T-3's defect would have been caught, since nothing produced it at all.

The unreachable eight are the real finding

Six of the eight are unreachable for one reason: the schema rejects the input before the tool's check runs.

  T-8.geometry_fields   caches requires the four geometry fields
  T-8.no_addressing     topology requires addressing
  T-8.line_pow2         line_bytes is an enum of powers of two
  T-8.vipt_no_page      addressing requires page_bytes
  load.include_shape    the include schema requires the shape
  schema.unknown_type   the loader reports load.include_type first

That is D-46 again, in geometry rather than in group completeness. The tool carries a second layer of checks duplicating schema required lists, and that layer is dead. D-46 documented the pattern for T-6 and recorded the boundary as uneven by decision. CLI-003 shows the unevenness is wider than T-6.

You have the same two options as before, and this time the measurement exists. Either the schema owns shape and these six go, or the tool owns them and the required lists come out so the readable message wins. What you should not leave is both, with the tool's copy unreachable, because that is a check nobody can test and everybody assumes is running.

If you keep them as defence in depth, the Guard assertion is only a partial tripwire. It fails when an existing fixture starts producing a Guard code. It stays silent if a schema requirement is removed and no fixture happens to reach it. Worth knowing before you rely on it.

T-8.field_sum is different and should go. tag_bits is assigned pa_bits - offset_bits - index_bits and the check asks whether the three sum to pa_bits. It is an identity. It is also the check that would have had to catch S-12 from INFRA-001, where tag width had three disagreeing sources. A check written against its own derivation cannot detect a disagreement, because there is only one source by the time it runs. If you want the S-12 class caught, the comparison has to be against something independently declared, and nothing currently is.

T-7 has no code at all

The R-3 list carries T-1 through T-6, T-8 and T-9. There is no T-7.

Port occupancy is enumerated as a tool check in cgen_decisions and in PROJECT_STATUS, and it emits nothing. CLI-002 said it records occupancy and reports nothing. You have since ruled one port, one edge. So T-7 is now a real check with a real error condition and no diagnostic, and the new coverage test cannot see its absence because coverage measures codes, not checks.

Going the other way, topology.addressing is a code with no T number. The enumeration and the code list disagree in both directions. The fix is to make the T-numbered enumeration and the code list the same artifact, which is the same move R-3 just made one level down.

The IA's Deferred Work makes the general version of this point about Q-07 and it is the sharpest line in the results: a check that does not exist is invisible to coverage.

## Background

The C++ validator, pboettch json-schema-validator, implements JSON
Schema draft 7 and discards the $schema declaration rather than
erroring on it. The five schema files were authored declaring
2020-12. That mismatch has been carried in four documents as a
standing hazard since session 002 and was never resolved.

It has now been resolved by inspection. The schemas were searched
for the two keywords whose behaviour differs between the two drafts
in a way that could matter here, unevaluatedProperties and a
keyword sitting as a sibling of $ref. Neither appears. The two
drafts therefore agree on every construct these five files use, and
the tool has been validating them correctly all along.

The $schema declarations were then corrected to draft 7 by hand, as
a PA-direct correction, session-003. That edit is the subject of
R-1 and is expected to be already present in the tree.

### R-4, the coverage test

cli/tb/test_diag_codes.cpp, Diagnostics.EveryCodeHasAFixture, named

then walks the list:

```

  Guard    the code must NOT be in the union. A guard a fixture
           reaches is a misclassification, not a pass
  Env      the same
```

The Guard direction matters as much as the Fixture direction. Without
it a code could be quietly demoted to Guard and the suite would stay
green. With it, a demotion that is wrong fails immediately.

other direction, a code emitted without appearing in the list.

configurations at all, so a broken fixture path cannot make every
code look uncovered for a reason that has nothing to do with the
tool.
